# MonoTest — Виписка транзакцій та синхронізація історії

Android-застосунок із картковим екраном у стилі monobank, посторінковим завантаженням історії операцій, окремими таймлайнами для кожної картки та спільною випискою за всіма картками.

Основний фокус у проєкті — надійна робота з локальним кешем у Room та вирішення проблеми «дір» у виписці (коли після паузи на сервері з'явилося більше операцій, ніж вміщує одна сторінка, або коли історія однієї картки завантажена глибше за інші).

## Стек технологій

- **UI:** Jetpack Compose, Material 3, Shared Element Transitions, кастомні анімації карток при скролі та свайпі, ефекти розмиття (`Haze`)
- **Архітектура:** MVVM / MVI (`AccountViewModel`, однонаправлений потік даних через `StateFlow` та `AccountAction`)
- **Локальне сховище:** Room (`tx` для операцій та `card_sync` для стану синхронізації карток)
- **Асинхронність:** Kotlin Coroutines, Flow (`combine`, `flatMapLatest`, `Mutex`)
- **DI:** Koin
- **Тестування:** JUnit 4, `kotlinx-coroutines-test`, AndroidX Room In-Memory testing

## Що реалізовано в застосунку

### 1. Єдине сховище без дублювання даних
Усі транзакції зберігаються в одній централізованій таблиці `tx` у Room. Дублікати на рівні БД відсікає `OnConflictStrategy.IGNORE` (разом із первинним ключем `id` та унікальним індексом по глобальному порядковому номеру операції `seq`), а сторінка від сервера, що перетинає вже завантажене вікно, відхиляється репозиторієм як порушення контракту (`check(...)`).

### 2. Чому обрано такий підхід до синхронізації (і чому без Paging 3)
На старті розглядався стандартний `Paging 3` із `RemoteMediator`, але для умов цього завдання він підходить погано:
- тут потрібно одночасно будувати і окремі стрічки для кожної картки, і загальну стрічку за всіма картками з однієї таблиці;
- у карток може бути різна глибина завантаженої історії, через що у загальній стрічці легко отримати пропуски між операціями різних карток;
- логіку закриття «дір» після довгої паузи значно простіше контролювати й тестувати у звичайному репозиторії.

Замість складного збереження списку розірваних інтервалів для кожної картки обрано простішу і надійнішу модель — **одне неперервне вікно історії на картку**:
- у таблиці `card_sync` для кожної картки зберігаються межі вже завантажених даних: `oldestSeq` (найстаріша завантажена операція), `newestSeq` (найновіша) та прапорець `reachedEnd` (чи дійшли до кінця історії);
- кожна завантажена сторінка записується в базу атомарно в одній транзакції Room (`@Transaction savePage`) разом із оновленням меж у `card_sync`;
- оскільки вікно розширюється тільки послідовно від країв (вниз при скролі або вгору при оновленні), всередині діапазону `[oldestSeq .. newestSeq]` пропуски неможливі.

### 3. Як працюють «діри» у виписці та їх довантаження

#### Сценарій А: Після перерви нових операцій більше, ніж на одну сторінку
Коли користувач робить pull-to-refresh або відкриває виписку картки, викликається `refresh(card)`. Репозиторій запитує у мокового API нові операції (`api.newer`) після поточного `newestSeq` сторінками по 20 елементів:
- якщо нових операцій небагато (до 20 штук), вони завантажуються за один запит;
- якщо за час паузи накопичилося, наприклад, 55 нових операцій, перша сторінка повертає `hasMore = true`. Репозиторій бачить, що між локальною базою та актуальним станом сервера є «діра», виставляє прапорець для UI (з'являється плашка *«Завантаження пропущених операцій…»*) і в циклі довантажує наступні сторінки (20 + 20 + 15), поки `hasMore` не стане `false`;
- кожна проміжна сторінка зберігається атомарно. Якщо посеред завантаження пропаде мережа або користувач закриє екран, вже завантажена частина залишиться цілісною, а наступний `refresh` продовжить рівно з того місця, де зупинився.

#### Сценарій Б: Історія однієї картки завантажена глибше за інші
У користувача є три картки: Чорна, Біла та Платинова. Якщо відкрити Чорну картку і проскролити її на 3 сторінки вниз (довантажити глибшу історію), а потім переключитися на загальну виписку за всіма картками, просто показувати всі записи з таблиці `tx` не можна — тоді у нижній частині списку будуть тільки операції Чорної картки, а операції Білої та Платинової за цей самий час будуть пропущені.

Щоб уникнути таких «дір», загальна стрічка (`observeAll()`) бере **перетин завантажених вікон усіх карток**:
- нижня межа загальної стрічки — це `max(oldestSeq)` серед усіх карток, які ще не дійшли до кінця своєї історії;
- верхня межа — `min(newestSeq)` по всіх картках.

Тобто загальний таймлайн показує лише той діапазон, де дані гарантовано є по всіх картках. А коли користувач гортає загальну стрічку вниз, метод `loadMoreAll()` знаходить картку з найменшою глибиною історії і довантажує сторінку саме для неї, поступово розширюючи спільне вікно.

### 4. Обробка помилок та захист від паралельних запитів
- **Автоматичний retry:** кожен запит до API загорнутий у невеликий механізм повторних спроб (до 3 разів із затримкою 200 мс / 400 мс при `IOException`). Якщо помилка тимчасова, користувач її навіть не помітить.
- **Ручний повтор у UI:** якщо всі спроби завершилися помилкою, у верхній частині виписки з'являється банер із повідомленням та кнопкою **«Повторити»**, яка перезапускає останню дію.
- **Синхронізація запитів:** для кожної картки використовується окремий `Mutex`, тому паралельні виклики `refresh` та `loadMore` не конфліктують між собою і не дублюють мережеві запити. При пагінації вниз передається `expectedOldest`, щоб відсікати зайві виклики під час швидкого скролу.

## Як перевірити роботу прямо в застосунку

Для зручної перевірки всіх граничних випадків у застосунок вбудована **Демо-панель**. Вона дозволяє в один клік змоделювати появу великої кількості нових операцій на сервері, різну глибину карток або падіння мережі.

### Крок 1. Окремі виписки та звичайна пагінація
1. Запустіть застосунок. На головному екрані відображається карусель із трьох карток (**Чорна**, **Біла**, **Платинова**) та прев'ю останніх 3 операцій для кожної з них.
2. Натисніть кнопку **«Усі»** над списком операцій (або на саму картку прев'ю), щоб розгорнути повну виписку обраної картки.
3. Проскрольте список вниз — біля нижнього краю з'явиться індикатор *«Завантаження історії…»* і підвантажиться наступна сторінка (по 20 операцій). Якщо доскролити до самого початку історії картки, внизу з'явиться підпис **«Це все»**.

### Крок 2. Загальна виписка за всіма картками
Перейти до загального таймлайну за всіма картками можна трьома способами:
- натиснути кнопку **«Усі картки»** у правому верхньому куті головного екрана;
- всередині відкритої виписки перемкнути верхній фільтр-чип на **«Усі картки (перетин вікон)»**;
- на головному екрані (на першій картці) зробити свайп вправо — поверх екрана плавно виїде загальна стрічка з ефектом розмиття фону.

Зверніть увагу на номери операцій у заголовках (наприклад, `#300`, `#299`, `#298`...): у загальній стрічці операції з різних карток ідуть строго по порядку без жодних пропусків.

### Крок 3. Симуляція «діри» після паузи (+55 нових операцій)
1. На головному екрані натисніть на круглу аватарку **«M»** у верхньому лівому куті — відкриється **Демо-панель (Statement Gaps)**.
2. Натисніть кнопку **«1. +55 нових на сервері»**. У статистиці панелі з'явиться позначка червоним кольором, що на сервері є 55 несинхронізованих операцій (це 3 сторінки при розмірі сторінки 20).
3. Натисніть зелену кнопку **«2. Відкрити виписку й довантажити діру»** (або просто закрийте панель, відкрийте виписку картки й потягніть список вниз).
4. Угорі списку з'явиться синій банер **«Завантаження пропущених операцій…»**. Застосунок за 3 послідовні запити до API підтягне всі 55 нових транзакцій, проскролить список до найсвіжішої операції (`#355`) і сховає банер.

### Крок 4. Перевірка різної глибини історії карток
1. Відкрийте **Демо-панель** (кнопка **«M»**) і натисніть **«Чорна глибше на 3 сторінки (+60 рядків)»**.
2. Подивіться на статистику вікон у панелі: у Чорної картки нижня межа `oldestSeq` стала значно меншою, ніж у Білої та Платинової.
3. Закрийте панель, відкрийте виписку Чорної картки та перемикайтеся між чипами **«Чорна картка»** та **«Усі картки (перетин вікон)»**:
   - в окремій виписці Чорної картки доступна вся глибока історія;
   - у загальній виписці відображається лише спільне вікно без пропусків, а при скролі вниз довантажуються Біла та Платинова картки, наздоганяючи Чорну.

### Крок 5. Симуляція помилки мережі та кнопки «Повторити»
1. Відкрийте **Демо-панель** і натисніть червону кнопку **«Наступний запит впаде (IOException)»** (вона змусить наступні 3 мережеві спроби впасти з помилкою).
2. Також можете натиснути **«1. +55 нових на сервері»**, щоб під час оновлення було що завантажувати.
3. Закрийте панель, перейдіть у виписку й потягніть список вниз (pull-to-refresh).
4. Після 3 автоматичних спроб retry з'явиться червона плашка з описом помилки та кнопкою **«Повторити»**. Натисніть **«Повторити»** — запит успішно виконається, і нові дані з'являться у списку.

### Крок 6. Скидання даних
У будь-який момент у Демо-панелі можна натиснути **«Скинути БД та демо-дані (Reset)»** — локальна база Room очиститься, моковий сервер перегенерує початкові 300 операцій (по 100 на кожну картку), і застосунок завантажить чисті перші сторінки.

## Тестування

У проєкті написані модульні та інструментальні тести, які перевіряють роботу репозиторію та бази даних у різних сценаріях.

### Запуск Unit-тестів
```bash
./gradlew testDebugUnitTest
```
У файлі `app/src/test/java/com/example/monotest/StatementRepositoryTest.kt` зібрано **14 тестових сценаріїв** з використанням `InMemoryStatementDao`:
1. Перше відкриття картки (завантаження рівно однієї сторінки `older`).
2. Пагінація вниз (`loadMore`) без дублікатів та зі збереженням порядку.
3. Закриття «діри» у 55 нових операцій після паузи за 3 послідовні виклики `newer` (20 + 20 + 15).
4. Різна глибина завантаження карток: перевірка, що глибокий «хвіст» однієї картки не потрапляє у спільну стрічку, а `loadMoreAll` довантажує саме найменш глибоку картку.
5. Часткове оновлення: нові операції однієї картки не з'являються у загальній виписці, поки не синхронізована інша картка.
6. Падіння мережі (`IOException`) на другій сторінці під час закриття «діри»: перевірка, що перша сторінка збереглася коректно, а повторний виклик добудовує вікно до кінця.
7. Два паралельні виклики `refresh` для однієї картки (відсутність гонитви та дублікатів завдяки `Mutex`).
8. Два паралельні виклики `loadMore` з однаковим `expectedOldest` (виконується лише один мережевий запит).
9. Досягнення кінця історії (`reachedEnd = true`) та відсутність зайвих запитів при подальшому скролі.
10. Коректна робота спільної стрічки, якщо одна з карток порожня (0 операцій) або має менше операцій, ніж розмір сторінки.
11. Операції з однаковим часом (`time`) на межі сторінок — нічого не губиться і не дублюється.
12. Дублікати на рівні БД відсікає `OnConflictStrategy.IGNORE` (а сторінка, що перетинає вікно, відхиляється репозиторієм як порушення контракту).
13. Серія з 30 випадкових дій (`refresh`, `loadMore`, додавання нових операцій, випадкові мережеві збої) з перевіркою цілісності даних після кожного кроку.
14. Скасування корутини (`CancellationException`) посеред багатосторінкового довантаження «діри» з подальшим успішним відновленням.

```bash
./gradlew connectedDebugAndroidTest
```
